## D. Function security design

No replacement function body is provided here.

### `public.admin_toggle_owner_verification(uuid, boolean)`

Future reviewed design should require:

1. Explicitly reject a missing authenticated identity, missing profile, NULL role, or unresolved role before any mutation.
2. Explicitly allow only the intended administrator role(s), checked against the canonical role source. Do not rely on nullable `NOT IN` logic as the sole deny condition.
3. Validate the target establishment and authorized scope. A caller must not verify an unrelated owner’s establishments through a broad owner parameter.
4. Affect only the requested establishment identity (or another explicitly approved scope). Do not automatically create a default establishment as a side effect of verification.
5. Preserve AP-24 compatibility: verification state belongs to each establishment independently; one owner may have multiple establishments.
6. Use a fixed, safe search path with schema-qualified object references as appropriate; review object ownership and avoid unsafe caller-controlled name resolution.
7. Revoke unnecessary execution from PUBLIC/anon/authenticated and grant only the required trusted role after checking actual RPC callers. Any client-invokable administrator action must still perform server-side role checks.
8. Record the privileged action through a trusted audit path without allowing client-supplied actor/role claims.

Supplied Query 8 confirms the function definition summary, owner, SECURITY DEFINER state, search path, NULL-sensitive guard, owner-wide update, and default-establishment creation behavior. Query 9 confirms PUBLIC ACL and effective EXECUTE for anon, authenticated, and service_role. Remaining work is to trace all callers and dependencies, then test missing-profile and authorized/unauthorized cases in non-production. No exploit is claimed.

### `public.current_user_role()`

Supplied Query 8 confirms postgres ownership, SECURITY DEFINER, `search_path=public`, a text return type, and lookup of `public.profiles.role` for `auth.uid()` with `tourist` fallback when no matching role is found. Query 9 confirms PUBLIC ACL and effective EXECUTE for anon, authenticated, and service_role. Role mutation/signup protections and application callers still require tracing and behavior tests.

## E. Profile privacy design

Separate a deliberately public, minimal directory projection from private account/profile state. Candidate **data classes** for review (not a claim about exact deployed column names):

- **Public candidate:** display name or other explicitly approved directory display fields only.
- **Private contact:** email and phone, supported as existing profile columns by supplied I-2; never expose by default solely because a profile is public.
- **Authentication identifier:** profile/auth UUID, which is an identifier and not an authorization secret.
- **Device/delivery token:** Query 4 confirms `fcm_token` is an actual `public.profiles` column and effective SELECT is true for anon, authenticated, and service_role. Treat it as private and restrict it to a necessary delivery path; do not expose it in public projections.
- **Planning preferences:** budget, category interests, location/origin and group details where stored; private to the tourist and narrowly scoped services. Do not assume these are profile columns; deployed evidence places planning data in separate overlapping tourist tables.

Design options requiring schema/API review include column-level grants or a purpose-built public view. A view does not automatically fix access if the base table remains exposed through grants, other views, RPCs, or exposed schemas; view ownership/security options also affect RLS semantics. Define which roles can select each field, how public directory queries are served, and how private fields are excluded from serialization. Regression-test profile display, authentication, contact editing, and role-management flows before changing privileges.

## F. Audit-log integrity design

Design objective: untrusted tourist/owner clients cannot assert privileged administrator actions or choose arbitrary actor identity. Trusted server/database code should derive the actor from the authenticated context, validate action and target against the operation, and write the audit event atomically with the privileged mutation where feasible. Client submissions, if any, should be treated as user reports/requests rather than authoritative audit history.

Restrict mutation/deletion of authoritative audit rows; separately define trusted writers, Super Administrator review, retention, and which metadata is safe to store. Avoid reservation notes, contact information, tokens, or other unnecessary sensitive payloads. Exceptional access to tourist-entered reservation details must itself be purpose-limited and audited under AP-22. Current authenticated INSERT and Super Administrator read are supplied policy summaries; they do not establish whether actors are server-derived or logs are append-only.

## G. Existing reservation security design

### Existing establishment-side `public.reservations`

Keep this workflow distinct from future tourist-entered information about external arrangements. The owner-supplied contract includes `tourist_id`, `itinerary_id`, `establishment_id`, `destination_id`, `eta`, `pax_count`, `reservation_status`, `service_name`, and `created_at`; it is an establishment-side process, not the AP-01 draft/event table.

Future policy review should define each command separately: tourist access to their own booking rows; owner access through the row’s establishment and verified owner relationship; administrator operations; and Super Administrator oversight. Verify canonical role strings against the role helper and stored role contract. The `establishment` versus `owner` mismatch is confirmed by supplied Query 7 and the profile role constraint: allowed values are `tourist`, `owner`, `administrator`, and `super_admin`, while the INSERT policy tests for `establishment`. The actual outcome for owner operations still requires behavior tests. Supplied Query 7 has no tourist UPDATE or DELETE policy; Query 10 nevertheless confirms SQL UPDATE and DELETE privileges. RLS and grants must be assessed separately. Do not infer tourist row mutation rights from `tourist_id` alone.

I-3 confirms two `reservations.itinerary_id → itineraries(id) ON DELETE SET NULL` constraints: `reservations_itinerary_fk` and `reservations_itinerary_id_fkey`. Their origin, necessity, dependencies, and safe remediation are unknown. Preserve them pending separate catalog/migration-history/dependency review. Independent FKs for `tourist_id` and `itinerary_id` do not prove both references belong to the same tourist. A same-owner invariant needs explicit database/write-path and RLS design plus negative tests; it is not established by ordinary FKs.

### Future tourist-entered reservation-event records

Under AP-01–AP-26, these records belong to an owner-scoped persisted draft/itinerary aggregate and remain private to the tourist by default. Establishment owners do not gain access because an event names their establishment; Tourism Office has no default private-detail access; Super Administrator/support access is exceptional, legitimate, restricted, and audited. Ownership must be derived from session/parent, with parent-child owner equality enforced. Do not reuse or extend `public.reservations` to represent these external arrangements without a separate approved design decision (current policy explicitly says not to reuse it).

## H. Safe remediation sequence

This sequence is design guidance only; every migration or production change requires separate authorization.

1. **Use the supplied catalog baseline:** Queries 1 through 11 are substantially supplied. Query 2/3 excerpts were truncated; retain that limitation and record any catalog visibility errors. Do not repeat supplied queries as an unresolved prerequisite.
2. **Trace current application dependencies:** identify profile fields and RPC/table operations used by screens/services; trace every itinerary, stop, reservation and audit write path. Do not reduce grants before this inventory.
3. **Prioritize confirmed urgent boundaries:** profile exposure across all listed columns/three roles; PUBLIC execution of SECURITY DEFINER functions; broad relation privileges including TRUNCATE/TRIGGER; audit authorship; policy unions; reservation role mismatch; and `service_role` BYPASSRLS. Perform controlled non-production behavior tests before designing remediation.
4. **Design profile privacy boundary:** decide public fields and private fields, then compare column-level privileges versus a carefully scoped public projection. Verify base-table, view, RPC, and exposed-schema behavior together.
5. **Consolidate RLS policies:** specify one coherent operation matrix for itineraries/stops and other tables, accounting for permissive OR unions, `WITH CHECK`, parent ownership, role memberships, grants, owner/bypass contexts, and RLS not forced. Regression-test before production.
6. **Design least-privilege grant changes:** Query 10 confirms all seven tested privileges for anon/authenticated/service_role on the nine inspected relations. Compare with actual application operations and trusted workflows; propose operation-specific changes only after dependency tracing and tests. Handle TRUNCATE/TRIGGER separately from row-level CRUD.
7. **Harden function execution:** after caller inventory, define missing-identity rejection, explicit role scope, target ownership, safe search path, and minimal EXECUTE ACL. Regression-test authorized and unauthorized cases.
8. **Review existing reservation integrity:** inspect duplicate FK provenance/dependencies and same-owner relation; separately define tourist/owner/admin operations and role strings. No blind constraint deletion.
9. **Plan AP-24 as its own compatibility workstream:** assess all owner-specific queries, `maybeSingle()` assumptions, dashboards, verification functions, RLS predicates, creation/management workflows and data preservation before altering `owner_id` uniqueness.
10. **Design future draft/event RLS separately:** only after parent schema, lifecycle, retention, and identity contract are approved. Enforce tourist-only private access according to AP-01–AP-26; do not grant default event-detail access to establishments or Tourism Office.
11. **Prepare reviewed additive migration only after readiness gates pass:** include backup/rehearsal/rollback and exact post-change catalog checks. Do not replay legacy migrations or treat this report as migration authorization.
