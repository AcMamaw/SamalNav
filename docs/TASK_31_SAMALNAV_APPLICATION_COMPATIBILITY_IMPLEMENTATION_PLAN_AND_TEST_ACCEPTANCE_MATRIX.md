# Task 31 — SamalNav Application Compatibility Implementation Plan and Test Acceptance Matrix

**Project:** SAMAL NAV
**Basis:** Tasks 26–30, especially the owner decision consolidation in Task 30, plus a read-only inspection of current Flutter models, services, screens, and tests.
**Status:** Planning only. No source changes, migrations, SQL, database access, or tests were performed for this task.

## 1. Executive summary

The owner-selected D29-01–D29-17 architectural directions can be mapped to current application work, but the application is not yet compatible with the proposed ten-relation Scope A contract. Main conflicts are client-authored role/audit/settings operations; legacy destination and verification states; a single-establishment lookup despite one-to-many ownership; required tourist-planning values despite nullable profile decisions; reviews represented as destination-only or in-memory samples without moderation; and server reservation/payment workflows that are excluded from the approved scope.

The planned core relations remain `profiles`, `destinations`, `establishments`, `location_verifications`, `tourist_details`, `favorites`, `reviews`, `events`, `audit_logs`, and `system_settings`. Payments, server-side reservations, server-side itinerary persistence, and CARS evidence tables remain excluded. Tourist-entered pre-booked details are local Hive itinerary data, are not SAMAL NAV reservations or confirmations, and must be retained as fixed constraints by MO-GA. Manual destination selection and circuit-planning workflows remain separate and must continue to work.

Task 30 records architectural selections, not complete field contracts or implementation authorization. D29-07/08 lifecycle vocabularies, D29-11 travel-mode vocabulary, D29-12 exact rating bounds, D29-13 transitions, A-09 audit/settings policy, A-11 retention details, and A-14 security validation remain gates. A-15 non-production initialization and A-16 production deployment are deferred and unauthorized.

### 3.1 Additional application contracts

**Authentication and roles (A-01/A-02):** `lib/services/role_service.dart` (`fetchCurrentUserRole`, `ensureTouristProfile`) reads a profile role with user metadata fallback and client-upserts a tourist profile. `lib/models/app_role.dart` defines the application role vocabulary. `lib/services/super_admin_service.dart` (`updateUserRole`) directly updates profile role. Compatibility requires trusting only the server-provisioned profile role, removing user-controlled metadata as an authority, and routing privileged changes through a trusted operation. This is security-sensitive and blocked on A-14 review and the approved Auth trigger contract.

**Establishment cardinality:** `lib/services/establishment_service.dart` (`getMyEstablishment`) filters by owner and calls `.maybeSingle()`, contradicting the selected one-owner-to-many-establishments contract. The owner dashboard `lib/screens/establishment_owner_screens/establishment_dashboard.dart` must show/select an establishment ID; service calls must carry that ID and verify ownership. `lib/services/establishment_dashboard.dart` should be audited for duplicate dashboard logic.

**Pre-booked itinerary details:** `lib/models/itinerary_draft.dart` and `lib/services/local_itinerary_draft_store.dart` represent local drafts, stops and transfer intent but do not expose a dedicated pre-booked commitment record in the inspected contract. Add a local Hive-compatible commitment value and backward-compatible serialization only in a separately authorized code task. It must not create a server `reservations` row or claim external confirmation. MO-GA must treat commitments as fixed itinerary constraints and preserve them through optimization.

**Manual/circuit and CARS boundaries:** preserve `lib/algorithms/manual_selection_workflow.dart`, `lib/algorithms/manual_selection_moga_adapter.dart`, `lib/algorithms/moga_engine.dart`, `lib/algorithms/system_generated_draft_builder.dart`, and screens `plan_page.dart`, `system_generated_planning_page.dart`, `system_generated_draft_review_page.dart`, `cars_recommendation_review_page.dart`. Keep manual destination selection and circuit planning usable without CARS or server itinerary persistence. CARS provider/preparer remains unavailable/insufficient where policy or verified evidence is missing; do not use public display rating/price, fallback records, or local review samples as numeric evidence.

## 6. Obsolete payment and server-reservation workflows

Owner scope excludes payment persistence and actual SAMAL NAV reservations. Current application code still depends on both:

- `lib/services/establishment_service.dart`: `getOverviewStats`, `getArrivalAlerts`, `getReservations`, `updateReservationStatus`, `getPayments`, and `markPaymentPaid` query or mutate excluded relations.
- `lib/models/reservation_record.dart` and `lib/models/payment_record.dart` represent those workflows.
- `lib/screens/establishment_owner_screens/establishment_dashboard.dart` includes booking and payment navigation/tabs, payment metrics, and reservation/payment display.
- `lib/services/administrator_service.dart` uses reservation row count as `totalVisits`, which is not an approved metric under the ten-relation scope.
- `lib/screens/admin_screens/administrator_dashboard.dart` and `lib/screens/admin_screens/super_admin_dashboard.dart` must be checked for labels/metrics that imply actual booking or settlement.

Compatibility work should remove those server queries and misleading booking/payment controls or replace them with owner-approved, non-booking establishment tools. The exact dashboard replacement is a product choice and must not be guessed. Do not create a substitute server reservation table. Tourist pre-booked details remain local Hive itinerary data, user-entered and unverified by SAMAL NAV; MO-GA preserves them as fixed constraints. They do not create reservations, confirmations, payments, or provider-side changes.
